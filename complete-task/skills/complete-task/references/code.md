# 検証プレイブック: コード実装

成果物がリポジトリ内のソースコードのとき、完了条件を**機械的に**検証する手順。

## 1. 検証コマンドを特定する

次の順で探し、**このリポジトリで実際に動くコマンド**を確定させる。推測で書かない — 一度実行して通ることを確かめる。

| 手掛かり | 見るもの |
|---|---|
| `CLAUDE.md` / `AGENTS.md` | プロジェクト固有のコマンド指定。最優先 |
| `Taskfile.yml` | `task --list` で一覧。`task test` `task lint` `task fmt` が典型 |
| `Makefile` | `make help` またはターゲット名を直読み |
| `package.json` | `scripts` の `test` `lint` `build` `typecheck` |
| `go.mod` | `go build ./...` `go test ./...` `go vet ./...`、`golangci-lint run` |
| `pyproject.toml` | `pytest`、`ruff check`、`mypy` |
| `.github/workflows/` | **CI が実際に何を実行しているか**。ここが最も信頼できる |

CI の実行内容と手元のコマンドが食い違うときは、**CI 側を正とする**。手元で通っても CI で落ちるなら完了ではない。

## 2. 実行順

前の工程が落ちたら次に進まない。原因が前工程にあるのに後工程のログを読むと時間を無駄にする。

1. フォーマット（`task fmt` / `go fmt ./...` / `prettier --write` 等）
2. 静的解析・lint（`golangci-lint run` / `ruff check` / `eslint`）
3. 型チェック（`tsc --noEmit` / `mypy`）
4. ビルド（`go build ./...` / `npm run build`）
5. テスト（`task test` / `go test ./...` / `pytest`）

## 3. 完了条件のテンプレート

タスク固有の条件に、次を**必ず加える**。

- [ ] テストが全通過する（実行コマンド: ___）
- [ ] lint / 静的解析のエラーが 0 件（実行コマンド: ___）
- [ ] ビルドが成功する（実行コマンド: ___）
- [ ] `git status --short` の変更が意図した範囲のみ（無関係なファイルが混じっていない）
- [ ] 新規・変更した挙動にテストがある（テストのないコードは検証手段がない）
- [ ] 挙動が変わった箇所のドキュメント・コメントが追随している

## 4. 差分を確認する

```bash
git status --short
git diff --stat
git diff
```

`git diff --stat` に**意図していないファイル**が出ていたら、その理由を突き止めるまで完成にしない。自動生成物・ロックファイル・エディタ設定が混じるのは典型的な事故である。

## 5. レビュー 3 視点の観点（コード向け）

- **A 正確性** — ロジックの誤り、境界条件（空・0・1 件・最大件数）、エラーハンドリングの欠落、型と実データの不一致、命名と実体の不一致、並行処理の競合
- **B 利用者目線** — 呼び出し側の開発者と運用者から見て、シグネチャが使いやすいか、エラーメッセージから原因が分かるか、既定値が安全か、後方互換が壊れていないか、ログが調査に足りるか
- **C リスク・抜け漏れ** — 完了条件に対する抜け、副作用（DB・ファイル・外部 API）、データ喪失とロールバック手段、認証・認可・入力検証、個人情報の取り扱い、テストが通っても本番で壊れる条件（並行数、データ量、タイムゾーン、文字集合）

## 6. やってはいけない

- テストを通すためにテストを緩める（アサーションの削除、`skip`、期待値を実測値に合わせる）
- lint エラーを `nolint` / `eslint-disable` で黙らせる（抑止するなら理由をコメントで残し、報告に書く）
- 実行していないコマンドの結果を書く
- 「たぶん通る」で完成宣言する
