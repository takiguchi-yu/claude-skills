# 検証プレイブック: 調査・資料作成

成果物が文書（レポート、設計書、手順書）のとき、完了条件を**出典突合**で検証する手順。

## 1. 一次情報の定義

事実主張は、次のいずれかにもとづいて書く。これ以外は「未確認」である。

| 種類 | 出典の書き方 |
|---|---|
| リポジトリのコード・設定 | `path/to/file.go:120-135` |
| 公式ドキュメント・仕様 | URL（版・日付が分かるなら添える） |
| コマンドの実行結果 | 実行したコマンドと出力の抜粋 |
| ロックファイル・マニフェスト | `package-lock.json` / `go.sum` の該当行 |
| ユーザーが明言した事実 | 「ユーザー指定」と明記（裏取り不要） |

**記憶を一次情報にしない。** バージョン、API シグネチャ、設定キー、料金、制限値は必ず現物で裏を取る。

## 2. 完了条件のテンプレート

- [ ] すべての事実主張に出典がある（出典なしの断定文が 0 件）
- [ ] 裏が取れなかった項目は「未確認」「推測」と明示し、確認方法（実行すべきコマンド、読むべきファイル）を添えている
- [ ] 章立てに抜けがない（目的で挙げた論点が全て本文で扱われている）
- [ ] 相反する情報源があった場合、両方を示して判断根拠を書いている
- [ ] 成果物のパスが合意どおり

## 3. 検証の手順

`ct-verifier` に次をやらせる。文書は「読んで良さそう」では検証にならない。

1. 本文から**事実主張を 1 文ずつ抜き出す**（断定文、数値、バージョン、手順のステップ）
2. 各主張に付いた出典を**実際に開いて**、その主張を支持しているか確かめる
3. 出典が主張を支持しない / 出典がない主張を列挙する
4. 目的で挙げた論点と本文の章を突合し、扱われていない論点を列挙する

出典が URL のときは WebFetch で実際に取得する。取得できなければ「出典検証不能」として ⚠️ にする。

## 4. レビュー 3 視点の観点（資料向け）

- **A 正確性** — 出典と主張の食い違い、数値の誤り、バージョンの取り違え、引用の文脈切り取り、古い情報の混入
- **B 利用者目線** — 読者（誰か明示されているか）が前提知識なしで読めるか、手順が上から順に実行できるか、前提条件・環境が書かれているか、失敗したときの分岐が書かれているか、用語が一貫しているか
- **C リスク・抜け漏れ** — 目的に対する論点の抜け、都合の悪い情報の欠落、反対意見や制約の未記載、個人情報・機密情報の混入、判断を誤らせる断定

## 5. やってはいけない

- 記憶で数値やバージョンを埋める
- 出典を「たしかこのあたり」で書く（行番号を確かめずに書く）
- 未確認を断定文に混ぜて量を稼ぐ
- 個人情報（氏名、メールアドレス、電話番号、社員 ID）を成果物に書く
