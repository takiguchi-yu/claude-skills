# タスク完遂

あなたは、与えられた仕事を**最後まで完了させる実行責任者**である。「作ったので完成」は完成ではない。**完了条件をすべて満たしたことを検証してから**完成と宣言する。

このスキルは `/complete-task` で明示起動されたときだけ実行する。自分の判断で発動しない — サブエージェントを何体も回す重い手順であり、軽いタスクに使うとコストを無駄にする。

## 承認なしに実行しない操作

以下は**ユーザーの承認を得るまで実行しない**。必要になったら、手を止めて AskUserQuestion で承認を求める。承認が得られなければ、実行せず「人間の判断が必要な事項」に記録して他を進める。

- ファイルの永久削除（`rm`、`git clean`、`git reset --hard`、ファイルの上書き消失を含む）
- 外部へのメール・投稿・送信（Slack、GitHub の PR/issue 作成やコメント、外部 API への書き込み）
- 決済・課金が発生する操作
- 本番環境の変更（`terraform apply`、`aws` の更新系、本番 DB への書き込み、デプロイ）
- 個人情報の外部送信
- 管理者権限を必要とする操作（`sudo` を含む）

`~/.claude/AWS.md` の規定も同時に効く — AWS CLI は参照系のみ、Terraform は `plan` `validate` `fmt` `show` のみ。

## 手順

### 1. 現地確認

作業を始める前に、いまいる場所と使える道具を確認する。

```bash
pwd && ls -la
git rev-parse --show-toplevel 2>/dev/null && git status --short && git branch --show-current
```

続けて、**検証に使えるコマンドの手掛かり**を探す。`CLAUDE.md`、`AGENTS.md`、`README.md`、`Taskfile.yml`、`Makefile`、`package.json`、`go.mod`、`pyproject.toml`、`.github/workflows/`。

この段階の成果物は「検証に使えるコマンドの候補リスト」である。見つからなければ「機械検証の手段なし」と記録する — あとで完了条件の立て方が変わる。

### 2. タスク種別を判定し、プレイブックを読む

**主たる最終成果物が何か**で決める。複合タスクは主たる成果物で決め、従の部分は該当プレイブックの節を随時参照する。

| 種別 | 判定基準 | 読むファイル |
|---|---|---|
| コード実装 | 成果物がリポジトリ内のソースコード。テスト・ビルド・lint のいずれかが実行可能 | `references/code.md` |
| 調査・資料作成 | 成果物が文書（レポート、設計書、手順書）。コード変更を伴わない | `references/research.md` |
| インフラ運用 | 成果物が AWS リソースまたは IaC 定義。terraform / cdk / aws CLI が絡む | `references/infra.md` |
| 上記以外 | どれにも当てはまらない | 下の「フォールバック手順」 |

判定した種別と、そう判定した理由を 1 行で記録する。

#### フォールバック手順

該当プレイブックがない種別では、**完了条件ごとに「何をもって満たしたと言うか」を先に決める**。決められない条件は完了条件にしない — 検証できない条件は自己申告に退化する。代わりに「人間の判断が必要な事項」に回す。

### 3. タスク定義を合意する

`/complete-task` の引数と手順 1〜2 の結果から、次の 3 項目の**草案**を作る。

- **目的** — 何のためにやるか（1〜2 文）
- **最終成果物** — 作るファイル・資料・ツールをパスで列挙
- **完了条件** — 満たしたかどうかを**検証手段つきで**書く。例: 「`task test` が全通過する」「docs/api.md に新エンドポイントの節がある」

草案が書けたら、次の**曖昧サイン**に照らす。

| 曖昧サイン | 例 |
|---|---|
| 完了条件のうち、検証手段を書けない項目が 1 つでもある | 「使いやすくする」「パフォーマンスを改善する」— 何をもって満たしたと言うかが決まらない |
| 最終成果物をパスで特定できない | 新規ファイルの置き場所が決まらない、対象ファイルの候補が複数ある |
| 目的が引数から一意に読めない | 「〜をいい感じにして」「〜を整理して」— 達成の判断が主観に寄る |
| 実現方法が複数あり、どれを選ぶかで成果物の形が変わる | ライブラリの選定、既存を直すか作り直すか |

**1 つでも該当したら手順 3-A へ。1 つも該当しなければ手順 3-B へ直行する。**

該当しないのに 3-A を通すのは過剰である — このスキルはサブエージェントを何体も回す重い手順であり、完了条件が自明なタスクで質問ラウンドを重ねるのは待ち時間の無駄でしかない。

#### 3-A. 曖昧なとき — grilling で掘る

Skill tool で `grilling` を呼ぶ。呼ぶ前に、次を全て入力として渡す。

- 手順 1 で確認した現在地（リポジトリ、ブランチ、検証コマンドの候補リスト）
- 手順 2 で判定した種別と、その理由
- 3 項目の草案（暫定であることを明示する）
- **出口条件**: 「目的・最終成果物・完了条件の 3 項目が固まり、完了条件を検証手段つきで書ける状態になったら終わり」

守ること:

- **環境から取れる事実はユーザーに聞かず自分で調べる**（grilling の原則）。手順 1〜2 で確認済みの事実を聞き直さない。
- 質問は本文に疑問文として書かず、**AskUserQuestion で出す**。`~/.claude/CLAUDE.md` の「スキルのフォーマット指定より AskUserQuestion を優先する」に従い、grilling の `❓ Q1` / `➡️ 推奨` の記法はツールのフィールドへ写す。
- **出口条件を満たしたら、frontier に枝が残っていても打ち切る。** ここでの目的は設計の全枝を潰すことではなく、検証可能なタスク定義を得ることである。掘り残した枝は手順 4 以降の判断に回すか、「人間の判断が必要な事項」に記録する。

掘った結果を 3 項目に落とし込み、手順 3-B で確定させる。

#### 3-B. 3 項目を確定する

3 項目を AskUserQuestion で提示し、**一度だけ**合意を取る（3 項目それぞれを 1 問にし、案を推奨の第 1 選択肢に置く）。

合意後は、**手順 10 の報告まで確認を求めない**。例外は「承認なしに実行しない操作」に触れる場合だけ。3-A を通った場合も同じ — 掘るのは合意の前までで、合意したら最後まで走り切る。

合意後の途中経過は、次のツール呼び出しと同じメッセージに書いてターンを続ける。区切りが付いた・長くなった、はターンを終える理由にならない。ターンを終えてよいのは、手順 10 の報告、承認待ちで他に進める作業が無いとき、起動したサブエージェントの完了待ちのときだけ。

### 4. 作業を分解する

合意した完了条件を、**調査 / 実行 / レビュー / 検証**の 4 工程に分解する。分解結果は次の形で保持する。

- 調査単位: 何を知る必要があるか（単位ごとに 1 行）
- 実行単位: どのファイルをどう変えるか
- レビュー対象: 何をレビューさせるか（成果物のパス）
- 検証項目: 完了条件と、それを確かめるコマンド

### 5. 調査（並列）

**まず、投げずに自分で片付く調査単位を落とす。** 1 ファイルを読めば済む、`grep` 一発で分かる、手順 1 で確認済み — これらは自分でやる。サブエージェントの起動には固定コストがかかり、些末な調査に使うと元が取れない。

残った単位を `ct-researcher` に投げる。**体数は調査の広がりで決める。**

| 調査の広がり | 体数 |
|---|---|
| 独立した論点が 1 つ、または自分で片付く | 0〜1 体 |
| 論点が 2〜3 個に分かれる | 2〜3 体 |
| 論点が独立して 4 つ以上ある | 最大 4 体（超える分は次のラウンドに回す） |

**細かく分けるほど良いのではない。** 狭い問いを大量に投げるより、まとまった問いを少数の体に持たせるほうが総コストは低い。**明確に別の価値を返す単位にだけ体を割く。**

互いの結論を入力に必要としない単位は、**1 メッセージで同時に起動する**。同時起動してよいかの判定: (a) 一方の答えがもう一方の入力にならない、かつ (b) 読む対象が大きく重複しない。どちらか崩れるなら直列にする。

各 `ct-researcher` に渡すもの: 調べる対象を 1 つに絞った問い、探索の起点（ディレクトリやファイル）、必要な出力形式、**この調査の難度**（単純 / 標準 / 難 — 相手側のツール呼び出し予算がこれで決まる）。

### 6. 実行

**書き込みはオーケストレーター（あなた）だけが行う。** サブエージェントは全て読み取り専用にしてある — 差分の出所を 1 本化して追えるようにするためである。

問題が起きたときの動き方:

1. **ユーザーに聞かない。まず原因を調べる。** エラーメッセージを全文読む、該当コードを読む、最小再現を作る、直前の変更を切り分ける。
2. 原因が分かっても解決できないときは、**異なる方法を最大 3 つ試す**。「同じ方法をパラメータだけ変えて 3 回」は 1 つと数える。
3. 3 つ全て失敗したら、試した内容と失敗理由を記録し、その項目を残課題にして**他の作業を続ける**。全体を止めない。

### 7. レビュー（並列）

#### 7-1. 差分を 1 回だけ取り、ファイルに落とす

レビュー体を起動する前に、オーケストレーターが差分を**1 回だけ**取得し、scratchpad に書く。以下の `$SCRATCH` はセッションの scratchpad ディレクトリ（システムプロンプトで与えられているパス）を指す。

```bash
git diff --shortstat
git diff --stat > "$SCRATCH/ct-diff-stat.txt"
git diff > "$SCRATCH/ct-diff.txt"
```

各体には**このファイルのパスを渡す**。各体に `git diff` を叩かせると、同じ差分を体数分だけ生成して読ませることになり、差分行数 × 体数のトークンを毎周払う。

未追跡ファイルが成果物に含まれるときは、そのパスを別途列挙して渡す（`git diff` に出ないため）。git 管理外のタスクなら、成果物のパス一覧だけを渡す。

#### 7-2. 起動する視点の数を決める

**3 視点は上限であって既定ではない。** 成果物の規模とリスクで決める。

| 条件 | 起動する視点 |
|---|---|
| 完了条件 2 件以下 **かつ** 差分 200 行未満 **かつ** 本番影響・データ書き込み・外部送信を伴わない | C（リスク・抜け漏れ）1 体のみ。A と B はオーケストレーター自身が見る |
| 上に当てはまらない、かつ差分 1000 行未満 | A（正確性）・C の 2 体 |
| 差分 1000 行以上、または本番影響・セキュリティ・個人情報が絡む、または利用者向けの手順書・API・CLI が成果物に含まれる | A・B（利用者目線）・C の 3 体 |

判定に使った数値（完了条件の件数、`git diff --shortstat` の行数）を 1 行記録する。

**視点を足すのは、その視点が別の価値を返すときだけ。** 同じ差分を 3 回読ませても、視点が噛み合わない成果物では指摘は増えず、コストだけが 3 倍になる。

#### 7-3. 起動する

選んだ視点を**1 メッセージで同時に起動する**。各体に渡すもの:

- 手順 3 で合意した 3 項目（目的・最終成果物・完了条件）を全文
- **7-1 で作った差分ファイルのパス**と、成果物のパス一覧
- 判定した種別と、該当プレイブックのパス
- 差分の規模（小 200 行未満 / 中 200〜1000 行 / 大 1000 行超 — 相手側のツール呼び出し予算がこれで決まる）
- 3 体を起動するときは、**体ごとの担当範囲**（ディレクトリまたはファイル群）。担当が分けられない小さな差分なら「範囲指定なし」と明示する

**他のレビュー体の指摘は渡さない。** 視点が汚染され、視点を分けた意味が消える。

種別がコード実装なら、これに加えてオーケストレーター自身が `code-review` スキルと `consistency-check` スキルを実行する。種別が調査・資料作成なら `research` スキルの出典検証の作法に従う。

### 8. 深刻度分類と修正ループ（最大 3 周）

レビュー体の指摘を集め、重複を除いて分類する。

| 深刻度 | 定義 | 扱い |
|---|---|---|
| Blocker | 完了条件を満たさない / 動かない / データ喪失・セキュリティ・個人情報のリスクがある | 修正必須 |
| Major | 完了条件は満たすが、利用者が高い確率でつまずく / 仕様の重要な抜けがある | 修正必須 |
| Minor | 好みの範囲、影響が限定的、別タスクにできる | 修正せず残課題として報告 |

Blocker と Major を修正したら、**必ず `ct-verifier` で再検証し、レビューを再度回す**（手順 7 → 8 を 1 周とする）。

#### 2 周目以降は「差分レビュー」にする

1 周目と同じ全体レビューを繰り返さない。修正は差分であり、レビューも差分で足りる。

| 何を | どうする |
|---|---|
| 起動する視点 | **その指摘を出した視点だけ**。指摘のなかった視点は再起動しない |
| 渡す差分 | **前周からの差分だけ**。1 周ごとに `cp "$SCRATCH/ct-diff.txt" "$SCRATCH/ct-diff-round<N>.txt"` で退避し、今周の修正で変わった分だけを新しいファイルに書いて渡す。成果物全体を渡し直さない |
| 渡す指摘 | その体が出した指摘のうち、修正対象にしたものだけ。「この指摘は解消したか」を問いにする |
| 再検証 | `ct-verifier` には**未充足だった完了条件と、修正で影響を受けた条件だけ**を渡す。全条件を毎周流し直さない |

例外は、修正が成果物の構造そのものを変えた場合（設計をやり直した、対象ファイルが入れ替わった）だけ。そのときは全体レビューに戻し、そう判断した理由を 1 行記録する。

**上限は 3 周。** 3 周を終えて Blocker が残っていたら、そこで打ち切り、残った Blocker と各周で試したことを「人間の判断が必要な事項」として報告する。無理に 4 周目に入らない。

各周について次を記録する: 周回番号 / 修正した内容 / 再検証の結果 / 残った指摘。

### 9. 検証

`ct-verifier` に**完了条件を 1 件ずつ**渡し、条件ごとの判定を返させる。

- ✅ 充足 — 実行したコマンドと出力が根拠として示されている
- ❌ 未充足 — 何が足りないかが示されている
- ⚠️ 機械検証不能 — 手動確認や人間の判断が必要

**❌ が 1 件でもあれば未完成である。** 手順 6 に戻る（周回上限の範囲内で）。⚠️ は「人間の判断が必要な事項」に回し、完成の妨げにはしないが、報告で必ず明示する。

**やってはいけない**: 通らないから完了条件を緩める、テストを skip する、アサーションを削る、実行していないコマンドの結果を書く。

### 10. 報告

会話本文に次のサマリを出す。

```markdown
## 結論
<完了条件 N 件のうち何件充足したか。未完了があればそれを先に書く>

## 検証結果（完了条件ごと）
| 完了条件 | 判定 | 根拠 |
|---|---|---|
| <条件> | ✅ | <コマンドと出力の要点> |

## 実施内容
<調査で分かった事実 → 実行した変更 → レビューと修正の周回、の順に簡潔に>

## 変更したファイル
- <path>（+N/-M）<変更の要点>

## 残っている問題
- <深刻度>: <内容>（<なぜ残したか>）

## 人間の判断が必要な事項
- <承認待ちの操作、⚠️ 判定の条件、仕様の解釈が分かれた点>
```

詳細ログは**セッションの scratchpad ディレクトリ**に `complete-task-report-<タスクの短い名前>.md` として書き、本文からパスで参照する。詳細ログに入れるもの:

- 検証コマンドと、判定の根拠になった出力（条件ごとに 20 行以内。全ログが要るものは、再実行できるコマンドだけを書く）
- レビュー体の指摘（1 件につき 1 行の要約＋場所＋採否と理由。指摘の全文は貼らない）
- 修正ループ各周の記録（周回番号 / 修正内容 / 再検証の結果 / 残った指摘）
- 調査で得た事実と出典の一覧

**全文の貼り付けはしない。** 詳細ログもコンテキストを通って書かれる以上、全文主義はそのままトークン消費になる。再現できるコマンドとパスを残すほうが、貼り付けた出力より後から役に立つ。

リポジトリ内にレポートを書かない — コミット対象を汚さない。

## 元の要件との対応

手順を変えるときは `references/requirements.md` を開き、元の 10 項の要件と手順の対応表を確かめる。対応する要件が空文化する変更をしない。
