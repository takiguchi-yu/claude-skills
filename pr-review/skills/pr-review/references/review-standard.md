# 指摘を出す基準

`pr-review` のレビュー役（`pr-review-functionality` と `/code-review` の Spec）と、Standards 軸を見る本体が指摘を探すときと、
`pr-review` の手順 4 で採否を決めるときに読む。**どの回も、この文書の基準だけで選ぶ。**
基準が回ごとに変わると、拾う指摘も回ごとに変わり、再実行のたびに新しい指摘が出てくる。
回によって変わるのは、「出さないもの」の「4 回目以降のレビューでの B・C」だけ。

## 基準: この PR はコードの健全性を確実に良くするか

[Google Engineering Practices — The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html) に従う。

- 変更がコードの健全性を確実に良くしているなら、完璧でなくてもよい。「完璧なコード」は無く、「より良いコード」があるだけ。
- 細部の仕上げを作者に求めない。レビューに使う時間とトークンは、実装に回すほうが価値が高い。

指摘は、**この PR をそのままマージすると困ること**を探す。改善の余地を網羅的に探すのではない。

## 出すもの

| 区分 | 当てはまるもの | ラベル（comment-format.md） |
| --- | --- | --- |
| A. 壊れる | 正しさの誤り、仕様（issue の完了条件）の未達、セキュリティ・個人情報、データの喪失・破損、本番の条件（データ量・並行・既存データ）で壊れる | `issue (blocking)` |
| B. 健全性が下がる | この PR で入れた設計が層・責務を崩す（smell はこれに当たるものだけ）、必要以上に複雑、issue で頼まれておらず理由も書かれていない挙動の追加、変更した挙動にテストが無い、読み手を誤らせる名前・コメント・doc・エラー文言、PR 本文の主張（テスト済み・未カバー 0 件など）がコードと食い違う、文書化された規約への違反（ツールが強制しておらず、リポジトリの既存の書き方とも食い違わないもの） | 誤りなら `issue (non-blocking)`、よりよい形の提案なら `suggestion (non-blocking)` |
| C. 確かめたい | A か B に当たるかが、コードを読んでも決まらない（本番データの実態、仕様の意図、旧実装の挙動）。何を確かめれば決まるかを添える | `question` |

## 出さないもの

- **Nit** — 好み、磨き、書き方の揺れ、動くが別の書き方もできる、というだけのもの
- **既存と同型** — 同じ書き方・構造・命名がリポジトリに既にある（@PRACTICE.md: 一般論より既存の慣習が勝つ）
- **PR の前からある問題** — この PR が原因でもなく、この PR の変更で悪化もしない（FYI にとどまるもの）
- **作者が判断済み** — PR 本文やコメントで、理由を添えて見送りを明記している
- **根拠の無い推測** — 発生条件も、何を見れば決まるかも示せない懸念。本番データの件数など**確かめ方を示せるなら推測ではなく C** で出す
- **テストの網羅度そのもの** — 変更した挙動にテストはあるが、境界値を増やせる、退行検出力を上げられる、というだけのもの（変更した挙動にテストが無いのは B）
- **4 回目以降のレビューでの B・C** — 手順 4 で当てる。下の「両方に当たるとき」より先に当て、C も出さない（回数の数え方と理由は [`re-review.md`](re-review.md)）

## 両方に当たるとき

「出さないもの」と「出すもの」の両方に当たるなら、**A と C を優先する**。既存と同型の書き方でも、既存データや
本番の条件で壊れうる（A）、または本番データの実態が決まらない（C）なら出す — 書き方が既存と同じでも、
データの実態はこの PR のたびに確かめ直す価値がある。B は「出さないもの」が優先する。

## 迷ったとき

「この指摘が無いままマージされたら、誰かが後で困るか」で決める。困る人と場面を 1 文で書けないなら、出さない。
