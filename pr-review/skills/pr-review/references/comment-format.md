# コメントの書式

`pr-review` の手順 4（インラインコメント本文）と手順 8（submit の総評）、追跡（[`follow-up.md`](follow-up.md)）の F4〜F6 から読む。

## インラインコメントの書式

[Conventional Comments](https://conventionalcomments.org/) に従う。ラベルで「これは何の
コメントか」、装飾で「マージを止めるか」を先に出す。レビュイーは 1 行目だけで
対応の要否を判断できる。

```
<label> [(decoration)]: <一行の要点>

<なぜそうなのか。根拠は path:line か仕様 URL>
```

### ラベル

| ラベル | 使うとき |
| --- | --- |
| `issue` | 具体的な不具合・誤り。ユーザーに見える／見えないは問わない |
| `suggestion` | 改善の提案。**何をどう変えるか**を明示する |
| `question` | 懸念はあるが妥当か判断できない。答えを求める |
| `nitpick` | 好みの範囲。**pr-review では出さない**（[`review-standard.md`](review-standard.md) の Nit） |
| `todo` | 小さいが必要な変更 |
| `note` | 読み手に気づいてほしいだけ。常に非ブロッキング |
| `praise` | 良い点。**作らない** — 本当に良いと思ったときだけ書く |

### 装飾

- `(blocking)` — 直るまでマージしてほしくない
- `(non-blocking)` — 直さなくてもマージしてよい
- `(if-minor)` — 直すのが軽ければ直してほしい

装飾を省くと「どちらとも言っていない」になり、レビュイーが判断に迷う。**`issue` と
`suggestion` には必ず付ける。** `nitpick` `note` `praise` は定義上ノンブロッキングなので省いてよい。

### blocking かどうかの決め方

**マージしたら何が起きるか**で決める。区分とラベル・装飾の対応は [`review-standard.md`](review-standard.md) の
「出すもの」表に従う（A が `(blocking)`、B が `(non-blocking)`）。

**全件が `(blocking)` になったら、一度並べ直す。** 本当に全部がマージを止めるほどなら
それでよい（壊れた PR は実在する）。だが多くの場合は「重要度を伝えたつもりで、
優先順位を伝えていない」状態になっている。レビュイーは全部が最優先だと言われると、
どれから手を付けるか決められない。

逆に、**blocking を怖がって全部 non-blocking にしない。** 仕様未達を non-blocking で出すと、
直されないままマージされる。

### 例

```
issue (blocking): b が 0 のとき ZeroDivisionError で落ちる

`div` は除数を検査していない。同じモジュールの `mul` は `app.py:8` で 0 を弾いて
いるので、ここも揃えるのが自然に見える。
```

```
suggestion (non-blocking): `retryCount` 引数は定数にすると引数が 1 つ減る

呼び出し元は `src/client.ts:88` の 1 か所だけで、常に 3 を渡している。
```

```
question: ここでリトライしないのは意図的か

呼び出し元の `src/client.ts:88` は一時的な失敗を想定しているように読めた。
```

### 書くときの決まり

- **根拠を必ず入れる**（@EVIDENCE.md）。`path:line`、仕様の URL、リポジトリ内の同型コードのいずれか。
  根拠を取りきれない懸念は `question` にして、何を確かめれば決まるかを書く。
- 1 スレッド 1 論点。同じ行に 2 つの論点があるなら本文を分けず、**別々のコメントにしない** —
  同じ行に複数スレッドは付けられるが読みにくい。要点を 1 つに束ねるか、片方を総評へ回す。
- 断定しすぎない。コードだけで確信が持てないものは `question` にする。

## submit の総評（メンション付き）

submit の `body` がそのままメンション付きコメントになる。**1 行目に disclaimer、2 行目に
メンション。**

```
🤖 Claude Code が作成したレビューです（内容は投稿者が確認済み）。

@<PR author の login> レビューしました。<全体の所感を 1〜2 行>

**要対応 <n> 件 / 提案 <n> 件 / 質問 <n> 件**（インライン <n> 件・総評 <n> 件）
<再レビューで由来を付けたときだけ: 修正コミットで入った指摘 <n> 件 / 前回見落としていた指摘 <n> 件>

<行に紐づけられなかった指摘があればここに書く。無ければこの節ごと省く>
```

- 件数は、投稿したインラインコメントと総評に書いた指摘の合計。括弧の内訳とあわせて実数と合わせる。合わないと信用されない。
  区分は上から順に当て、最初に当たったもので数える: `(blocking)` が付いたもの → 要対応、`question` → 質問、
  残り（`(non-blocking)` `(if-minor)` の `issue` `suggestion`、`todo`、`note`）→ 提案。
- 総評に書く指摘にも、区分に合わせたラベル（`question:` など）を付けて数える。
- 由来の件数も、インラインと総評の合計で数える（上の件数と合計が一致する）。
- 前回の見落としがあったことは隠さずに数える。
- **行に紐づかない指摘の置き場所がここ**。ファイル横断の設計上の指摘、diff に現れない
  「足りていないもの」（テストが無い、ドキュメント未更新）はインラインにできないので総評へ。
- 所感で誇張しない。指摘ゼロなら「気になる点は見つからなかった」と素直に書く。

## 追跡中の返信

[`follow-up.md`](follow-up.md) の手順 F4〜F6 で、確認が通らなかった指摘に返すとき。人の確認を経ずに投稿するので、
**1 行目の disclaimer でそれを明かす。**

```
🤖 Claude Code が自動で確認・作成した返信です（投稿者は未確認）。

<何を確かめたか。返信で示されたコミット・issue・出典のどれを読んだか>
<何が残っているか、または何を求めるか。根拠は path:line>
```

- 総評への返信は PR の会話コメントになり、宛先が分からなくなるので、2 行目の先頭で `@<PR author の login>` をメンションする。
- 相手の主張を、確かめた結果で受ける。「〜とのことですが」で始めず、読んだもの（`path:line`・SHA）から書く。
- F5 の見直しで足す指摘は、インラインコメントと同じ `<label> [(decoration)]: <要点>` の行を 3 行目に置く。

## approve の本文

[`follow-up.md`](follow-up.md) の手順 F5 で approve するとき、F6 で approve を出し直すとき。

```
🤖 Claude Code が自動で確認し approve しました（投稿者は未確認）。

@<PR author の login> 指摘 <n> 件の対応を確認しました。

- resolve <n> 件（うち指摘の誤り <n> 件）/ 総評 <n> 件を確認
- 確認した commit: <見直した head の短縮 SHA>
```

- 件数は追跡台帳（`follow.md`）の行と合わせる。指摘の誤りだった件は隠さずに数える。
- 指摘ゼロのレビューを approve するなら、2 行目は「気になる点は見つからなかったので approve します」にし、件数の行を省く。
- F6 で出し直すなら、2 行目は「approve の後に積まれた <短縮 SHA> を確認したので、approve し直します」にし、件数の行を省く。
