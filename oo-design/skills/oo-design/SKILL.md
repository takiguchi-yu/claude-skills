# オブジェクト指向設計の原則とパターン検討表

@DESIGN.md の設計パス（概念・責務・依存の向き）を通すときの語彙と判断基準。
**設計パスを通す条件と、見送りの記録義務は @DESIGN.md 側にある。** ここは中身だけ。

## 原則

- **単一責任** — 1 つのモジュールが変更される理由は 1 つ
- **カプセル化** — 状態と、その状態を変える操作を同じ場所に置く。不変条件はオブジェクトの内側で守り、
  呼び出し側に「正しい順番で呼ぶ」責任を負わせない
- **継承より合成** — GoF 自身が挙げる原則。振る舞いの差し替えは、まず合成と委譲で考える
- **依存は抽象に向ける** — 具象への直接依存を減らし、依存の向きを外側（I/O・フレームワーク）から
  内側（ドメイン）へ揃える
- **値オブジェクト** — 意味のある値を裸の `string` / `int` で引き回さない
- **深いモジュールと両立させる** — 小さいインターフェースの裏に厚い実装を置く。
  語彙と判断基準は `codebase-design` スキル、ドメインの言葉の揃え方は `domain-modeling` スキルに従う
  （どちらも description はユーザーからの依頼を条件にしているが、@DESIGN.md の規定が優先する）

## 文書に適用するとどうなるか

原則はコード専用ではない。文書・手順書・スキル定義でも同じことを言っている。

| 原則 | 文書での読み替え |
|---|---|
| 単一責任 | 1 節 1 目的。その節が書き換わる理由は 1 つ |
| カプセル化 | 前提と結論を同じ節に置く。読者に「正しい順で読む」責任を負わせない |
| 依存は抽象に向ける | 具体例より先に判断基準を書く。手順の詳細に上位の方針を依存させない |
| 値オブジェクト | 意味のある概念に名前を付ける。「あれ」「この設定」で引き回さない |
| 深いモジュール | 短い見出しの裏に厚い中身。見出しを増やして薄くしない |

## GoF デザインパターン検討表

設計パスを通すとき、この構造に当てはまる既知のパターンがあるかを一度当てる。

| 困っていること | 検討するパターン |
|---|---|
| 生成の分岐が条件分岐で膨らむ | Factory Method / Abstract Factory / Builder |
| アルゴリズムを差し替えたい | Strategy |
| 既存のインターフェースが噛み合わない | Adapter |
| 振る舞いを後から重ねたい | Decorator |
| 状態によって振る舞いが変わる巨大な分岐 | State |
| 通知の宛先が増えていく | Observer |
| 骨格は同じで一部の手順だけ違う | Template Method |
| 木構造を一様に扱いたい | Composite |
| 複雑なサブシステムの入口を 1 つにしたい | Facade |
| 型ごとの処理を外に出したい | Visitor |

## 採らない判断の基準

**パターン名から設計を始めない。** 次のいずれかに当たるなら、素直に書く。

- **YAGNI** — 分岐が 2 つしかない、呼び出し元が 1 つ、差し替える予定が実際にない
- **浅くなる** — パターンを入れるとインターフェースが増え、モジュールが浅くなる
  （`codebase-design` の「深いモジュール」を壊すなら採らない）
- **言語の流儀に合わない** — GoF の実装形（クラス階層）をそのまま持ち込まず、
  **その言語の標準的な書き方へ翻訳する**

  | GoF の形 | 翻訳先 |
  |---|---|
  | Strategy | 関数値・高階関数 |
  | Decorator | 高階関数・ミドルウェア |
  | Iterator | 言語組み込みの反復（`for...of`、ジェネレータ、イテレータプロトコル） |
  | DI コンテナ | コンストラクタ引数・関数引数 |
  | Singleton | **既定で採らない**（グローバル状態を持ち込む） |

- **既存の設計と食い違う** — @PRACTICE.md の優先順位に従い、**既存の慣習が勝つ**。
  直しにいかず、乖離を報告に 1 行残す
