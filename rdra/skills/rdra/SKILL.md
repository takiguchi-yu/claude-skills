# RDRA で要件定義を組み立てる

振る舞いの仕様（R・T・S）の前段で、**何を作るか**を RDRA の要素のつながりで組み立てる手順。
依頼が無くても読む条件の正本は @SPEC.md 側にある。振る舞いの書式は `spec-notation` スキルが受け持つ。ここは中身だけ。

骨格は RDRA 公式の「要件定義の進め方」のフェーズ 1・2。フェーズ 3（条件・バリエーション）は `spec-notation` のデシジョンテーブルと状態遷移表に渡す。

```
[要求] 要求を確かめる → [0] As-Is を起こす（改修のときだけ）→ [1] フェーズ1: 洗い出す → 確認 → [2] フェーズ2: UC ⇄ 情報・状態を往復 → 確認 → [3] spec-notation へ渡す
```

## 進め方の構え

- **洗い出しが先、精度は後** — 各要素を作り込まず、全体を粗く出してから、要素どうしのつながりで精度を上げる
- **Claude が下書きする** — 依頼・コード・チケット・資料から下書きを作り、根拠の無いところだけを聞く。各要素の横に出典（`path:line`、チケット、資料名）を書く
- **根拠の無い要素** — 推測で埋めず、`[NEEDS CLARIFICATION: 何が分からないか（候補）]` を置く（`spec-notation` と同じ未決マーカー）
- **隣** — 変更する UC と同じ情報・状態につながる UC、同じ画面・イベントを使う UC。改修で詳しく描く範囲と `[KEEP]` の候補を、この語で決める

## 置き場と図

`.scratch/<feature>/rdra.md`、チケットがあればチケットに置く（@ISSUE.md）。図は Mermaid のコードで書く。

図の名前は公式のダイアグラム名にそろえる。各図に載せるものと Mermaid の型は、このスキルの決め（UC 複合図の画面・イベントだけは公式の Step 5 による）。

| 図 | Mermaid | 載せるもの |
| --- | --- | --- |
| システムコンテキスト | `graph` | システム・アクター（登場人物）・外部システム |
| ビジネスユースケース | `graph TD` | 業務 → BUC（ビジネスユースケース）→ アクティビティ。アクティビティに担当のアクターを添える |
| UC 複合図 | `graph LR`。UC は `([UC 名])` の楕円で描く | BUC ごとに 1 枚。アクター → 画面 → UC → 情報、外部システム → イベント → UC |
| 情報モデル | `erDiagram` | 情報と関連。情報はビジネスで ID を付けて管理しているものの単位で、テーブルと 1 対 1 にしない |
| 状態モデル | `stateDiagram-v2` | 情報が持つ状態。遷移のラベルに、その遷移を起こす UC の名前を書く |

UC の名前は「〈情報〉を〈動詞〉する」の形にする（このスキルの決め）。

UC のつながり（アクター・画面・イベント・情報）は UC 複合図で見せる。UC の表に残すのは、図に載らない出典とコードの場所だけにする（印は差分表）。

### ユーザーに見せる形

フェーズの終わりの確認は、毎回この形で出す（質問 UI で見えるものは @ASKING.md のとおり）。

1. `rdra.md` を書き終えてから、このフェーズの要の図を `diagram` スキルで描く。フェーズ 1 はシステムコンテキストとビジネスユースケース、フェーズ 2 は UC 複合図をアクター 1 人（または外部システム 1 つ）ずつに分けたもの。アクターと UC が多対多になると、mmd2txt の線が合流してどのアクターの矢印か読めなくなるため
2. AskUserQuestion の `question` には、`rdra.md` の絶対パス（ほかの図はここで開いて見る）、未決マーカーの一覧、このフェーズで決めたことの要約を書き、「この図で次へ進めてよいか」で終える。描いた図は、各選択肢の `preview` に同じものを入れる。アクターごとに分けた図は 1 つの `preview` に縦に並べ、4 つ以上あるときは UC の多い順に 3 つまでを入れて、残りは `rdra.md` で見てもらう
3. 選択肢は「このまま次へ進む」と「直す（直す点を Other に書く）」の 2 つにする。フェーズ 2 だけは「このまま次へ進む」を「要件定義をここで終える」と「spec-notation で仕様まで進める」の 2 つに分け、選択肢を 3 つにする。`description` には、終えると UC の一覧で対象と対象外が決まり見積もれること、仕様まで進めると条件・バリエーションまで詰めるので手戻りが減ること（チームが成熟していなければこちらを勧める。公式の進め方による）を書く

## [要求] 要求を確かめる

誰の何の困りごとを解くか（要求）を `rdra.md` の冒頭に 1〜3 行で書く。その下に、もう決まっている方針・制約（使う基盤、置き場、期限など）を書く。要求が依頼から読み取れなければ聞く。方針・制約は、依頼と資料から読み取れたものを並べたうえで、ほかに決まっているものがあるかを必ず 1 回聞く。資料に To-Be があるときは、その To-Be が今も有効かも同じ AskUserQuestion で聞く。資料に書かれていない前提ほど To-Be を左右するので、ここは「根拠の無いところだけ聞く」の例外にする。

完了条件: `rdra.md` の冒頭に要求と、方針・制約（無ければ「無し」）がある。要求には出典かユーザーの答えがあり、方針・制約にはユーザーの答え（読み取れたものの確認を含む）がある。資料に To-Be があるときは、それが今も有効かのユーザーの答えがある。

## [0] As-Is を起こす（改修のときだけ）

可視化だけの依頼では、変更範囲を「依頼された範囲」と読み替えて手順 4 まで進め、「ユーザーに見せる形」で図を見せて終える。

今の姿を RDRA の要素に起こす。変更範囲は、依頼で変わる画面・インターフェース・テーブルを起点に決める。粗く広く出す層と、詳しく出す層を分ける。

- **広く粗く** — アクター・外部システム・業務・BUC・アクティビティは、分かる範囲で網羅的に出す。To-Be の議論の幅と、変更が波及する先を見るため
- **詳しく** — 画面・イベント・情報・状態は、変更範囲とその隣に絞る

1. **入出力から UC を求める** — 画面ごとに使うアクターと UC を、外部とのインターフェース（API・バッチ・ファイル連携）ごとにイベントと外部システムと UC を挙げる
2. **データから情報を求める** — DB のスキーマから、ビジネスで ID を付けて管理しているものを情報として挙げる
3. **つなぐ** — 情報と UC をつなぎ、情報の状態を洗い出して遷移に UC を当てはめる
4. **コードに索引を付ける** — UC・画面・イベント・情報ごとに、実装しているディレクトリかファイルを書く
5. **To-Be を始める** — この図と表を写して To-Be の下書きにする。フェーズ 1 以降は To-Be を育てる。印はフェーズ 2 の差分表で付ける

完了条件: 変更範囲とその隣について、すべての画面とインターフェースが UC につながり、すべての情報が UC につながり、状態のすべての遷移に UC が付き、UC・画面・イベント・情報のそれぞれにコードの場所か未決マーカーがある。改修では、To-Be の写しがある。

## [1] フェーズ 1: 議論のベースを作る

1. **出発点** — システムに関わるアクターと外部システムを挙げ、システムコンテキストを描く。関わる業務を挙げ、システム化の対象がどのあたりかを書く
2. **スコープ** — 業務ごとに BUC と、そのアクティビティを粗く挙げる
3. **情報** — 業務で扱う情報を挙げ、システムで扱うものに印を付ける
4. **状態** — 業務が認識している状態を、思いつく範囲で挙げる

完了条件: アクター・外部システム・業務・BUC・アクティビティ・情報・状態が、それぞれ 1 件以上あるか「無し（理由）」と書いてある。すべての要素に出典か未決マーカーがある。

確認: 「ユーザーに見せる形」で出し、直しを受けてからフェーズ 2 へ進む。

## [2] フェーズ 2: 要件を組み立てる

5 と 6 を往復し、改修では最後に 7 を行う。下の完了条件をすべて満たし、かつ直近の 1 周で図に変更が無ければ抜ける。

5. **トップダウン** — 業務・BUC・アクティビティを見直し、アクティビティごとに `システム化する` / `しない` を決めて、システム化するものに UC をつなぐ。UC に関わるアクターから画面を、外部システムからイベントを足し、BUC ごとに UC 複合図を描く。ここで業務や BUC の見直しが要れば戻って直す
6. **ボトムアップ** — 情報どうしを関連づけて情報モデルを描き、欠けている情報を足す。情報が持つ状態から状態モデルを描き、欠けている状態を足す。情報と状態を UC につなぎ直し、UC が何をするかを確かめる

7. **差分表を更新する（改修のとき）** — 列は「種別・要素・印・出典」。種別はアクター・外部システム・システム・業務・BUC・アクティビティ・画面・イベント・UC・情報・状態・置き場。As-Is と To-Be の要素を 1 行ずつ入れ、`追加` / `変更` / `削除` / `変更なし` の印を付ける。印はこの差分表だけで見る（図はつながり、UC の表は出典とコードの場所を受け持つ）

完了条件:

- [ ] すべてのアクティビティに `システム化する` / `しない` の印がある
- [ ] システム化するアクティビティが、それぞれ 1 つ以上の UC につながっている
- [ ] すべての UC に、アクターか外部システム、画面かイベント、情報が 1 つ以上つながっている
- [ ] すべての情報が 1 つ以上の UC につながっている。つながらない情報は削るか、残す理由を書く
- [ ] 状態モデルのすべての遷移に UC が付いている
- [ ] 改修では、差分表に As-Is と To-Be のすべての要素が 1 行ずつあり、印がある
- [ ] 未決マーカーが残っていない（残ったものは AskUserQuestion で聞いた）。関係者に聞かないと答えの出ない未決は、確認の `question` の未決一覧に「関係者待ち」と書けば足りる

確認: UC の一覧（システム化の範囲）を添えて「ユーザーに見せる形」で出す。要件定義をここで終えるか、仕様まで進めるかを、この確認の選択肢で決めてもらう。「ここで終える」が選ばれたら、関係者待ちの未決を、誰に聞けば分かるか付きの申し送りにする。チケットに書き戻すか起票する（@ISSUE.md）。トラッカーが無ければ `rdra.md` の末尾に一覧にする。

## [3] spec-notation へ渡す

`spec-notation` で振る舞いを書く。対象の UC は、新規ではすべて、改修では差分表の印が `追加` / `変更` / `削除` のもの。

| RDRA の要素 | spec-notation で書くもの |
| --- | --- |
| UC と、つながる画面・イベント・情報 | EARS の要件（R）。主語は UC を受け持つシステム・画面 |
| 状態モデルのうち、@SPEC.md の状態遷移表の条件に当たるもの | 状態遷移表（S）。遷移のラベルの UC がイベントの列になる |
| UC を左右する業務のルール（条件）と、その軸になる区分・種別（バリエーション） | デシジョンテーブル（T）。バリエーションが条件の行になる |
| 改修で `削除` の UC | 消える振る舞いを「現状」に書き、代わりの振る舞いがあれば R にする |
| 改修で `変更なし` の UC のうち、隣にあるもの | `[KEEP]` の候補 |

完了条件: 対象の UC（`削除` を除く）すべてに R が 1 件以上あり、`削除` の UC すべてに「現状」の記述があり、`spec-notation` の網羅チェックを通っている。
