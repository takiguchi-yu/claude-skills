# 振る舞いの仕様の書式

@SPEC.md の「何を書くか」に当たったときの書式と網羅チェック。
**いつ書くか・どこに置くか・承認の扱いは @SPEC.md 側にある。** ここは中身だけ。

## 書く順序

1. **振る舞いを EARS で並べる** — 正常系・異常系・状態つきを 1 文 1 振る舞いで書き、R1 から ID を振る
2. **表に起こす** — @SPEC.md の表で当たったデシジョンテーブル・状態遷移表を作る。
   表で漏れが見つかったら、EARS に戻って要件を足す
3. **改修なら `[KEEP]` を足す** — 変更箇所の隣で、変えない振る舞い
4. **公開インターフェースなら契約を書く**
5. **決めきれない点に未決マーカーを置く**
6. **網羅チェックを通す** — 末尾の「網羅チェック」をすべて満たしたら完成

## EARS

1 文に振る舞いを 1 つ。行頭に ID と英語のラベル、文は日本語。主語は振る舞いの持ち主（システム名・画面名・関数名）。

| ラベル | 使う場面 | 書式 |
| --- | --- | --- |
| `[ALWAYS]` | 常に成り立つ | 〈主語〉は〈振る舞い〉する。 |
| `[WHEN]` | 出来事を契機に起きる | 〈契機〉とき、〈主語〉は〈振る舞い〉する。 |
| `[WHILE]` | ある状態の間だけ成り立つ | 〈状態〉の間、〈主語〉は〈振る舞い〉する。 |
| `[IF]` | 異常・望まない事態への対処 | 〈異常〉場合、〈主語〉は〈振る舞い〉する。 |
| `[WHERE]` | 機能・構成が有効なときだけ | 〈機能〉が有効な構成では、〈主語〉は〈振る舞い〉する。 |
| `[KEEP]` | 改修で変えない振る舞い。他のラベルの前に付ける | 元のラベルの書式のまま、振る舞いの前に「引き続き」を付ける。<br>例: `[KEEP][WHEN]` 〈契機〉とき、〈主語〉は引き続き〈振る舞い〉する。 |

- 複合はラベルを並べる — `[WHILE][WHEN] オフラインの間に保存ボタンが押されたとき、…`
- `[ALWAYS]` は原典の Ubiquitous に当たる独自ラベル（原典はキーワードを持たない）
- 契機・状態・振る舞いは検証できる語で書く — 「すぐに」より「1 秒以内に」、「適切に」より画面名・状態名・値
- 振る舞いが 2 つあれば ID を分ける。ID とテストを 1 対 1 で対応させるため

```text
R1 [WHEN]  保存ボタンが押されたとき、エディタは下書きを保存する。
R2 [WHILE] オフラインの間、エディタは送信をキューに積む。
R3 [IF]    保存に失敗した場合、エディタはエラーを表示し入力を保持する。
R4 [WHERE] 自動保存が有効な構成では、エディタは 30 秒ごとに下書きを保存する。
```

## デシジョンテーブル

条件とアクションを行、ルールを列（T1, T2…）に置く。記号は JSTQB に揃える。

- 条件: `T`（成り立つ）/ `F`（成り立たない）/ `-`（結果に影響しない）/ `N/A`（起こりえない）
- アクション: `X`（行う）/ 空欄（行わない）

| | T1 | T2 | T3 | T4 | T5 |
| --- | --- | --- | --- | --- | --- |
| 会員である | T | T | T | F | F |
| 合計 5,000 円以上 | T | F | F | - | - |
| 離島への配送 | - | F | T | F | T |
| 送料 0 円 | X | | | | |
| 送料 500 円 | | X | | X | |
| 送料 1,500 円 | | | X | | X |

網羅の確かめ方:

- **漏れ** — 各列が覆う組み合わせの数を足すと、全組み合わせの数（各条件が取りうる値の数の積）になる。
  `-` の列は、その条件の値の数だけ覆う。上の例は 2 + 1 + 1 + 2 + 2 = 8 = 2 × 2 × 2
- **重なり** — どの組み合わせも、当てはまる列がちょうど 1 つ
- **アクション** — どの列も、行うアクションが 1 つ以上ある

起こりえない組み合わせは列を作らず、表の下に「〜は起こりえない（理由）」と書き、漏れの計算に含める。

## 状態遷移表

行に現在の状態、列にイベントを置き、全セルを埋める。空欄は「決めていない」と区別できない。

| 現在 \ イベント | 支払う | 発送する | キャンセルする |
| --- | --- | --- | --- |
| 未払い | S1 → 支払い済み | ✕ | S2 → キャンセル済み |
| 支払い済み | ✕ | S3 → 発送済み | S4 → キャンセル済み（返金する） |
| 発送済み | ✕ | ✕ | ✕ |
| キャンセル済み | ✕ | ✕ | ✕ |

- 遷移するセルに S1, S2… を振り、遷移先と遷移時の動作を書く
- `✕` は受け付けない組み合わせ。受け付けないときの振る舞いを `[IF]` の要件として 1 つ書く
  （例: `R9 [IF] 受け付けない操作が要求された場合、システムは状態を変えずにエラーを返す。`）

## 変えない振る舞い（`[KEEP]`）

バグ修正・改修では、直す振る舞いと一緒に**変えない振る舞い**を書く。

```text
現状            会員の合計がちょうど 5,000 円のとき、システムは送料 500 円を請求している。
R1 [WHEN]       会員の合計がちょうど 5,000 円のとき、システムは送料を 0 円にする。
R2 [KEEP][WHEN] 会員の合計が 4,999 円のとき、システムは引き続き送料を請求する。
R3 [KEEP][WHEN] 会員でない利用者の合計が 5,000 円のとき、システムは引き続き送料を請求する。
```

- 「現状」は ID を振らない。直す対象であって、満たす要件ではない
- `[KEEP]` は変更箇所の隣から選ぶ — 同じ条件の境界値、同じ関数の他の分岐、変更する関数の呼び出し元
- `[KEEP]` に対応する既存のテストがあれば、ID を対応付けるだけでよい

## 契約（事前条件・事後条件・不変条件）

公開インターフェースを新設・変更するとき、インターフェースごとに書く。

```text
契約: calculateShipping(cart, address)
- 事前: cart の商品が 1 件以上ある。address は検証済み
- 事後: 戻り値は 0 以上の整数（円）
- 不変: cart を変更しない
```

- 事前条件を破られたときの振る舞いは、`[IF]` の要件として R に書く。呼び出し側が何を受け取るかは契約だけでは決まらない

## 未決マーカー

決めきれない点は `[NEEDS CLARIFICATION: 何が決まっていないか（候補）]` として要件の中に残す。

```text
R5 [WHEN] ログインに 5 回失敗したとき、システムはアカウントを
          [NEEDS CLARIFICATION: ロックの解除条件（15 分後 / 管理者の操作）] までロックする。
```

残ったマーカーは @SPEC.md に従って AskUserQuestion で聞き、答えで置き換える。

## ID とテスト

- ID は仕様 1 つ（チケット 1 枚・spec 1 本）の中で R1, T1, S1 から振る。
  別の仕様を参照するときは、仕様の識別子を前に付ける（例: `#12 R3`）
- ID ごとに 1 件以上のテストを対応させ、テスト名かコメントに ID を入れる
  （例: `R3: 保存に失敗したらエラーを表示し入力を保持する`）
- テストにできない ID は「テスト不能: 理由」と書く
- 完了条件は ID で書く（例: `- [ ] R1〜R5・T1〜T5 のテストが通る`）

## 文書に使うとき

スキル・CLAUDE.md などエージェント向けの文書でデシジョンテーブルを書くときは、
条件を左の列、処理を右の列に置き、行が組み合わせを漏れなく覆うことを確かめる。T/F の記号と ID は省いてよい。
形は @DECIDE.md の「根拠｜帯｜処理」表と同じ。

## 網羅チェック

すべて満たしたら仕様は完成。満たさない項目があれば、該当する節に戻る。

- [ ] すべての要件が `R<番号> [<ラベル>]` で始まり、文がそのラベルの書式に沿っている
- [ ] 失敗しうる `[WHEN]` には、失敗したときの `[IF]` がある
- [ ] デシジョンテーブルの列が全組み合わせを覆い、重なりが無い
- [ ] 状態遷移表に空欄が無い
- [ ] バグ修正・改修に `[KEEP]` が 1 つ以上ある
- [ ] 公開インターフェースごとに契約があり、事前条件を破られたときの `[IF]` がある
- [ ] すべての ID に対応するテストか「テスト不能: 理由」がある
- [ ] `[NEEDS CLARIFICATION: …]` が残っていない（残ったものは AskUserQuestion で聞いた）
